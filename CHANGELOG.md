# Changelog

All notable changes to this project are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and the project uses [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Design

- Specification of the first version in `docs/specs/` (SPEC-00 to SPEC-10, in Italian): scope, roles and the owner's decisions; platform and architecture; guild-only network protocol and trust rules; data model; the Accord tab in the guild window; extended roster, alts and contacts; professions and recipes; likes and the social index; guild bank; quality, spike and release; risks and open questions.
- Architecture decisions 0001–0018 in `docs/adr/`.
- Decisions confirmed by the owner: likes from account to account, irreversible and anonymous (only totals); alt list, BattleTag and Discord always shared with the guild; milestone order roster → professions → reputation → bank; name Azeroth Accord, GPL-3.0.

### Planning

- Development roadmap in `docs/roadmap/`: M0 spike to M6 release (50 steps) with branch, dependencies, scope, acceptance criteria, tests, docs and real-client checks, plus the V2 backlog.

### Addon

- M1.1: the addon skeleton `AzerothAccord/` (TOC 16001 with `AzerothAccordDB` / `AzerothAccordCharDB` and the AddOn Compartment, `embeds.xml` with Ace3, LibDataBroker and LibDBIcon, `Bindings.xml`, English and Italian locales, `Core/Init.lua` with the Forever check and `/accord` / `/acc` with `help`, `debug` and the view commands); `.pkgmeta`, `.luarc.json`, `tools/fetch_libs.py`, `tools/install_addon.py`, `tools/check_addon.py`, `tools/check_package.py` and the release workflow, adapted from Azeroth Guild Finder ([ADR 0018](docs/adr/0018-reuse-azeroth-guild-finder-foundations.md)); `docs/RELEASING.md`.
- M1.2: the offline test harness, adapted from Azeroth Guild Finder: `Tests/run_tests.py` (lupa 2.8, Lua 5.1), `Tests/lib/` (assertions, harness with `/reload` simulation), `Tests/mock/` (the mock client: core helpers and `bit`, clock, frames and events, timers, addon messages with lockdown, guild roster, player and build, `C_EncodingUtil`), `Tests/test_addon.lua` (boot, Forever check, locales, slash commands, `/reload` round trip) and `Tests/test_mock.lua`; CI runs them.
- M1.3: `Core/Compat.lua`, the only door to the game API (adapted from Azeroth Guild Finder): guarded calls and secret values, guild roster with the `C_Club` fallback and officer ranks, club fields (professions, Discord), player and BattleTag, party and raid members, own professions and recipes, the guild recipe directory, the guild bank and its logs, chat lockdown and restrictions, time and encoding; `Compat:Probe()` with the API table and the feature capabilities of SPEC-01 §5 (`available` / `missing` / `unknown`, refined by modules with `Compat:SetFeature`). `Core/Diagnostics.lua` and `/accord debug` (report in the chat for now, no names). The mock client gains club, group, trade skill and guild bank areas and secret values; every [verify] API is tested missing, erroring and secret.
- M1.4: `Core/Config.lua` (adapted from Azeroth Guild Finder: defaults, validation rules, step-by-step migrations, read-only for a newer schema, the account token in pure-Lua Base64, size estimates in `/accord debug`), `Data/GuildKey.lua` (`<realm>/<guild>` keys, one data table per guild, never mixed), `Core/Role.lua` (member, officer, Guild Master; `ROLE_CHANGED` and `GUILD_CHANGED` on the Bus) and `Core/Bus.lua`.
- M1.5: `Net/Codec.lua` with the `<version>|<TYPE>|<payload>` format of SPEC-02 (plain-text header, CBOR with optional Deflate in Base64, unknown types and newer versions ignored, types registrable by modules), `Core/Hash.lua` (SHA-256 and HMAC-SHA-256 in pure Lua with `bit`, checked against the FIPS 180-2 and RFC 4231 vectors), and `Net/Transport.lua` adapted from Azeroth Guild Finder for `GUILD`, `OFFICER` and `WHISPER` (priorities, per-distribution gap, one `HELLO` per five minutes, lockdown and restriction hold, keys, retries, the guild stamp of every message, the queue saved at logout and restored at login, own echoes ignored and the `OFFICER` echo as proof of the officer channel).
- M1.6: `Net/Store.lua`, the versioned records of the seven data sets per guild with the trust rules of SPEC-02 §6: first hand (with "same account" proved only by mutual listing in each character's own account record, ADR 0006 note), relays only from officers in the receiver's roster, authority sets (likes ledger, bank decisions, restricted tabs), co-play only from an observer in the pair and merged with a maximum, owner rules per set, shape and size checks, and retention (90 / 365 / 60 days).
- M1.7: `Net/Sync.lua`, the guild sync per author (SPEC-02 §4, ADR 0004 note): HELLO with an 11-byte summary per author at login and every 15–20 minutes, pushes from the authors' own accounts and from one designated officer for offline authors, REQ to a HELLO sender who is ahead with one answer on GUILD for everyone, local changes batched for 5 seconds, lost own data recovered from the guild. `Hash.Fast` for the digests. The network simulator `Tests/sim/` (adapted from Azeroth Guild Finder: one guild roster, real logouts and logins with SavedVariables, roster online status): 50 clients converge after 45 minutes of random logins, logouts, writes, lockdowns and 1% loss, inside the documented traffic budget.
- M1.8: the Accord tab and the panel shell (SPEC-04, ADR 0003): `UI/GuildTab.lua` (a fifth tab in the guild window under Blizzard's four, only for the guild and not minimized, the panel over the content area, Blizzard observed only with `hooksecurefunc` / `HookScript` and `SetDisplayMode` never called, fallback to the standalone window when the window's layout is not recognised), `UI/Shell.lua` (one panel moved between the tab and the window, navigation by registered views, top bar with the sync state and Pop out, welcome text while no view exists), `UI/Window.lua` (movable, resizable window remembered per character, Esc, `/accord`, the AddOn Compartment and the key binding), `UI/DiagnosticsBox.lua` (`/accord debug` in a selected, read-only box), `UI/Skin.lua` and `UI/Widgets/Base.lua` adapted from Azeroth Guild Finder to the client's own templates and fonts. `tools/check_addon.py` also requires an Italian string for every English one. Wiki: Interface Tour rewritten, new Commands page.
- M1.9: `docs/checklists/M1.md`, the in-game check of M1 for the owner (loading, `/accord debug`, the Accord tab and taint, combat, the window, saved data, two clients hearing each other). The `v0.1.0` section and tag follow the owner's confirmation.
- M2.1: `Data/Roster.lua`, the roster model (SPEC-05 §1, ADR 0010): one list of members merged from `GetGuildRosterInfo` / `GetGuildRosterLastOnline`, `C_Club.GetMemberInfo` (professions, Discord, member id, joined by GUID or name), the shared `recipes` and `accounts` records and the player's own professions, each profession marked `native`, `shared` or `own`; lazy rebuilds with `ROSTER_UPDATED` on the Bus, `C_GuildInfo.GuildRoster()` at most every 15 seconds, the `clubProfessions` / `clubDiscord` capabilities refined from what members show. A guild of 1000 members costs one pass per source. The mock client gains the playable classes and a real-clock helper for performance budgets.
- M2.2: `Data/Accounts.lua` (SPEC-05 §3, ADR 0006): every character that logs in joins the account's list (`chars`, `mains`) and publishes its own `accounts` record (token, characters on the realm with `inGuild`, main, version) after login, on level up and when the guild roster changes, without a new revision when nothing changed; always shared, no setting. Characters of other players are grouped by mutual listing (a forged list joins nothing), characters outside the guild appear as claimed, tokens that disagree are flagged, and public notes `main: <name>` / `alt: <name>` give hints for members without the addon. Renamed characters follow their new name and stale ones are dropped after 30 days, only once `GetPlayerInfoByGUID` has proved it answers. `Compat.Player.InfoByGUID`, the mock `GetPlayerInfoByGUID`, and the simulator option `accounts`.
- M2.3: the Roster view (SPEC-05 §1, SPEC-04 §2): `UI/RosterModel.lua` (columns, cell texts, sort by every column with missing values last, search by name and profession, filters for online, class, rank, profession and mains only, the grouped-by-account rows with expandable alts, saved choices in `char.ui`) and `UI/Roster.lua` (virtual rows, clickable headers, toolbar, column chooser, selection on the Bus); `W.Check` and `W.ShowMenu` widgets. `/accord roster` now opens it. The mock client runs OnShow / OnHide down the frame tree and moves children on `SetParent`, as the client does.
- M2.4: the member card (SPEC-05 §2): `UI/MemberCard.lua` opens on a click in the Roster table, beside it in a wide panel and over it (with Back) in a narrow one. Details (zone, last online, rank, public note, the officers' note only when `CanViewOfficerNote()` allows it, addon and version), professions with their source and age, all the characters of the same account (also outside the guild, each one opens its own card), and `Card.AddSection` for later steps. `Compat.Guild.CanViewOfficerNote` and the mock notes permission.
- M2.5: `Data/Contacts.lua` (SPEC-05 §4, SPEC-03 §2): the own BattleTag (`BNet_GetBattleTagSelf`, else `BNGetInfo`) and the typed Discord name published as one `contacts` record, always shared, with a retry for a late Battle.net service; the contacts of an account from the newest records of its characters, the native Discord name first, everything from the network validated and with `|` escaped. The member card gets a Contacts section: a click copies a contact through `UI/CopyBox.lua` and **[Add BattleTag friend]** calls `C_Club.SendBattleTagFriendRequest`. The first **Settings** view (`UI/Settings.lua`, `/accord settings`) has the Discord field; the table gets its Contacts column.
- M2.6: `Data/CoPlay.lua` (SPEC-07 §3.1, ADR 0008, D6): silent co-play recording from login on: every 60 seconds one minute to every pair of guild members in the party or raid (the player included, also inside instances), per realm day; members with hidden GUIDs are recognised by name through the roster or counted as unreadable, never guessed; published hourly, at logout and at the change of day in records of at most 100 pairs (each with a pair of the observer), merged with the maximum across observers, kept 90 days. `/accord debug` shows the counts; there is no view yet. `Compat.ServerDay`, the simulator option `coplay`.
- M2.7: `docs/checklists/M2.md`, the in-game check of M2 for the owner (what is not known yet and the fallback of each case, the roster table, professions from the game, the card and the officers' note, alts of two accounts, contacts and the friend request, co-play in a group and in an instance, two clients, taint). The member card also gets **[Make this my main]** on the player's own characters. The `v0.2.0` section and tag follow the owner's confirmation.
- M3.1: `Data/Recipes.lua`, the native recipe source (SPEC-06 §1, ADR 0010): the game's guild recipe directory (`C_GuildInfo.QueryGuildMemberRecipes`, `GUILD_RECIPE_KNOWN_BY_MEMBERS`, `GetGuildMemberRecipes`) behind the `guildRecipesNative` capability check, one query at a time (queue of 20 without duplicates, 2 seconds apart, 8-second timeout, a rest after 5 unanswered queries), answers cached in memory for 15 minutes and read as a list or a set of spell ids; a bitfield answer is recognised and switches the source off. The shared lists (M3.2 / M3.3) are a complete fallback that works alone; the choice between the sources waits for the M0.4 in-game results. `Compat.TradeSkill.GuildMemberRecipes` now passes the member and the skill line and returns every value.
- M3.2: `Data/RecipeScan.lua` and the list encoding in `Data/Recipes.lua` (SPEC-06 §1, §3, SPEC-03 §3, PRO-06): when a profession window opens or changes the own recipes are read (`GetBaseProfessionInfo`, `GetAllRecipeIDs` or the filtered list, `GetRecipeInfo(id).learned`), encoded as sorted spell ids in delta varints and Base64 (about 1.5 bytes per recipe before Base64), hashed with the skill rank, and published as one `recipes` record per character and profession when the hash changes, at most once every 10 minutes per profession (a change in the pause waits and goes out with the latest state). A filtered list can only add recipes, never remove them. The decoder refuses malformed text. The store refuses a `recipes` record whose id is not `<GUID>:<skill line>`; Cooking, First Aid and Fishing are published but are not profession cells in the roster.
- M3.3: recipe sync (SPEC-06 §1.4, SPEC-02 §4.7): the `recipes` set travels with the normal per-author sync, and `Recipes:Lookup` now reads one place for every view: the native answer first (with the age of the shared list too), else the member's shared list (the own scan for the player), decoded once per revision; `Recipes:ProfessionsOf`; `RECIPES_UPDATED` on the Bus for native and shared arrivals. New **on-demand request** `Sync:RequestSet(set, author)`: a `REQ` for one set by WHISPER to the author's account or up to two officers, answered by WHISPER to the asker only, once per 5 minutes per author and set, at most 20 answers a minute per sender; `Recipes:Ensure` asks every source a view can use and reports each one's status. Simulator: a 400-recipe list reaches 20 clients in under 10 s with about 1.3 KB sent in all, a late login stays inside the 8 KB login budget, an unchanged list costs nothing.
- M3.4: the recipe list (SPEC-06 PRO-01..PRO-03 §2.1): the profession cells of the Roster table show `Alchemy 285/300`, have a tooltip with the source and the age and open the new **Professions** view (`UI/Professions.lua`, `UI/RecipeModel.lua`) on a click; so do the profession lines of the member card. The list has an icon and a name per recipe (names and icons from `C_Spell.GetSpellInfo`, loaded on demand and redrawn once), the game's own recipe tooltip, search from the panel's box, a Category menu (recipes I know / do not know compared with your own list, categories when the client tells them), difficulty colours when the client gives them, and a message instead of the rows when there is no list (waiting, nobody online who has it, no addon, unknown profession) while every source is asked (`Recipes:Ensure`). `Compat.Spell` and `TradeSkill.RecipeMeta`, the mock spells (`Tests/mock/76_spells.lua`). Skill rank and maximum now show as `285/300`.
- M3.5: **who can craft** (SPEC-06 PRO-04 §2.2): `Data/Crafters.lua`, a reverse index from recipe to the guild members who know it, built lazily from every known list (`Recipes:AllLists`: native answers first, then the shared records and the own scan) and searched by recipe or item name (a pasted link counts as its name): exact names first, then prefixes, then the rest, at most 40 recipes and 120 crafters each, online members first and the characters of one account together. The Professions view now opens on this search (the panel's search box, "Online only", rows with profession, rank, source and age, a click on a member opens their recipes, Back returns to the search, each mode keeps its own search text); `/accord professions` opens it. A first search over 400 members with two 300-recipe lists takes about 250 ms. Spell-data requests for names are capped at 150 per 5 seconds.
- M3.6: **Request craft** (SPEC-06 PRO-05 §2.3) and `docs/checklists/M3.md`, the in-game check of M3 for the owner (every unverified API with its fallback: the native directory and the shape of its answer, the own scan APIs, the skill line ids, spell names and tooltips, categories, the whisper; the steps; the report table). A **Request craft** button on each recipe of an online member (in their list and under the recipe in *Who can craft*) opens the chat box with `/w <name>` and a message with the recipe link already written; the addon never sends it, and the button is not shown for offline members, the player's own recipes or recipe header rows. `Compat.Chat.OpenWhisper(name, text)`, `Recipes:CraftRequest` / `OpenCraftRequest`, `CRAFT_REQUESTED` on the Bus. Wiki: Professions and Recipes, FAQ and Commands. SPEC-10 Q8 records that the main recipe source waits for the M0.4 results. The `v0.3.0` section and tag follow the owner's confirmation.

### Spike

- M0.1: the probe addon skeleton `tools/probe/AzAc_Probe/` (TOC 16001, check registry S1–S11 as stubs, `/aacp list|run|export|reset`, export frame, `AzAc_ProbeDB`), `tools/install_probe.py` with `tools/local.example.ini`, and `docs/spike/README.md`.
- M0.2: probe check S1 (`Checks_GuildTab.lua`): `/aacp tab` adds a test tab and panel to the guild window using only hooks, dumps the window structure and the taint state, and logs `ADDON_ACTION_BLOCKED` / `ADDON_ACTION_FORBIDDEN`; `/aacp note` stores owner observations.
- M0.3: probe checks S2, S8 and S10 (`Checks_Roster.lua`): field statistics of `C_Club.GetMemberInfo` for the whole guild (counts only, online and offline, `discordInfo` shape, `bnetAccountId` sharing, realm parts of names), own BattleTag shape and `/aacp btag friend` on a volunteer, account-wide SavedVariables stamps across characters and realms.
- M0.4: probe checks S3 and S4 (`Checks_Recipes.lua`): the native guild recipe directory (`/aacp recipes guild`, API presence by namespace, `GUILD_RECIPE_KNOWN_BY_MEMBERS` timing, getters described by shape) and the own recipe scan with the profession window open and closed (`/aacp recipes own|open|auto`, counts and milliseconds).
- M0.5: probe checks S5 and S6 (`Checks_Messaging.lua`): test-prefix addon messages on GUILD, OFFICER and WHISPER (`/aacp ping|pong|burst|msgsize|whisper|msgs`) with result codes, own-echo latency, received runs with missing counts, and lockdown snapshots (`/aacp snapshot`, plus automatic logs on restriction, encounter and combat events).
- M0.6: probe check S7 (`Checks_Group.lua`): party and raid scans (`/aacp group`, `watch`) counting readable and secret `UnitGUID`, `UnitIsInMyGuild`, `GetRaidRosterInfo` fields, guild-roster GUID matches and scan cost, with `GROUP_ROSTER_UPDATE` gaps and delayed re-scans, and boss start and end.
- M0.7: probe checks S9 and S11 (`Checks_BankPerf.lua`): guild vault scan (`/aacp bank`: tab permissions, filled slots, item and money logs with time format, money, vault events with timing) and performance on generated data (`/aacp perf`: roster build, sorts, filter, social index, label propagation, serialization, memory).

### Repository

- Licence, code of conduct, contributing guide, issue and pull request templates, CI (documentation checks), the docs rule, the wiki sync and the advisory DCO check; `tools/check_docs.py`, `tools/check_pr_docs.py`, `tools/ship_step.py` and `tools/sync_wiki.py` adapted from Azeroth Guild Finder ([ADR 0018](docs/adr/0018-reuse-azeroth-guild-finder-foundations.md)).
- User manual skeleton in `docs/wiki/` (design phase).
- `tools/ship_step.py` no longer uses GitHub's squash merge, which authors the commit with the account's personal email and refuses the noreply address: it squashes the step locally into one noreply commit, lets CI check it in the pull request and fast-forwards `main` to it ([ADR 0012](docs/adr/0012-git-flow-and-automated-shipping.md)).
- CI downloads the libraries more reliably: `tools/fetch_libs.py` retries with exponential backoff on HTTP 429, 5xx and network errors (honouring `Retry-After`), and the workflow caches `AzerothAccord/Libs` keyed on `.pkgmeta` and `tools/fetch_libs.py`.
